## 1. "More like this" in the video viewer
Status: implemented
**What the user gets:** A button in the full-screen viewer that shows related videos from their own library.
**Why it fits:** Every record stores an embedding (`Collection.add`, src/collection.py). `Collection.search` already queries by embedding. The viewer fetches `/videos/info` (app.py `video_info`), which gives the button a home.
**Plan:** Add `Collection.similar(video_id, num_results, where)`. It gets the record's embedding with `include=["embeddings"]`, queries with it, and drops the video itself from the results. Add a `/videos/similar` route that applies `search_where(filters)` and returns cards the way search does. Add a "More like this" button in static/profile.js that loads those results into the grid.
**Files:** src/collection.py, app.py, static/profile.js, templates (if needed), test_collection.py
**Effort:** small
**Risks / open questions:** None significant. It must respect the active filters.
**Done when:** Clicking the button shows the nearest videos, without the source video and within the current filters. A test_collection.py test covers `similar` ordering and excluding the source video.
**Implementation notes:** Found already in the code: `Collection.search_similar`, `run_search(..., similar=)`, the `#viewer-info-similar` button and the similar chip in static/profile.js.

## 2. Failed videos list with retry or skip
Status: proposed
**What the user gets:** Users can see which videos failed to load and why, and choose to retry or skip them. Permanently broken videos stop being retried forever.
**Why it fits:** When `process_video` returns None, the app only prints a message (app.py sync worker). The sync state has `urls`, `loaded_urls` and `completed_urls` but no failures. `explain_error` (src/processor.py) already produces readable reasons.
**Plan:** Have processing surface the failure reason. Store `failed: {url: {reason, attempts}}` in the sync state, and skip URLs after N attempts unless the user retries them. Expose the failures in `sync_status_payload`. Add a collapsible list with Retry and Skip buttons on accounts.html / static/accounts.js, plus the routes behind them.
**Files:** app.py, src/processor.py, templates/accounts.html, static/accounts.js, test_sync_pause.py / test_processor.py
**Effort:** medium
**Risks / open questions:** The value of N (suggest 3). Whether a skip should persist across full re-syncs.
**Done when:** Failures show with reasons, skipped URLs aren't retried, and Retry re-queues a URL. Tests cover recording failures and the attempt cap.

## 3. Record every account that saved a video

**Why it fits:** `Collection.add` upserted a single `account_id`, so whichever account synced a video last owned it.
**Plan:** Per-account `acct_<id>: 1` metadata keys, an `accounts_where` filter, a startup backfill, and account deletion that keeps shared videos.
**Files:** src/collection.py, app.py, test_collection.py
**Effort:** medium
**Risks / open questions:** Videos that were taken over by another account before this fix only regain their original account on its next sync.
**Done when:** A shared video matches both account filters and survives deleting one account. Existing records are backfilled.
**Implementation notes:** Done in the main session. The account marker keys are handled in src/collection.py (`account_key`, `accounts_where`, `backfill_account_keys`, `delete_account_videos`). In app.py, `search_where` and `loaded_urls_for_account` now use them, and the backfill runs at startup. Added 3 tests to test_collection.py. Suite: 89 passed, 1 failure unrelated to this change (test_processor::test_transcribe).

## 4. Apply the sort to all search results
Status: proposed
**What the user gets:** Sorting search results by "most liked" or "newest" orders the whole result set, not just the page on screen.
**Why it fits:** The `run_search` docstring (app.py) says the sort is applied client-side to the visible page only (`sortShownResults`, static/profile.js). `library_videos` already sorts on the server.
**Plan:** When a sort is set, fetch the top-K relevant matches (for example 200), sort them on the server with the same key function `library_videos` uses, then paginate. Remove or limit the client-side re-sort.
**Files:** app.py, static/profile.js, a test file for run_search
**Effort:** small–medium
**Risks / open questions:** Choosing K, or a relevance-distance cutoff, so weak matches don't fill the sorted results.
**Done when:** Sorted search is consistent across pages, with a test covering it.
**Note (after #9/#10):** The cutoff question is mostly answered. `run_search` (app.py:907) now gets distances and returns `(page, has_more, has_weak)` through `page_matches` (src/collection.py:101). Sort only the strong matches (distance <= `WEAK_MATCH_DISTANCE`), up to K, and keep weaker matches after them behind "Show weaker matches", sorted in their own group. This is the same order `sortShownResults` (static/profile.js:729) already uses on screen. Phrase searches are never split, so they need only the top-K cap. Sort inside `page_matches`, or just before it, so that every offset (including `X-Search-Next-Offset`, app.py:1062) indexes the same stable sorted list.

**Plan:** Extend `parse_document` to return all sections and show the transcript and description in the viewer. Next, return a short snippet with each result showing the best-matching sentence for the query.
**Files:** src/video.py, app.py, static/profile.js, test_collection.py
**Effort:** small (viewer) / medium (snippets)
**Risks / open questions:** The document layout parsing is regex-based and brittle.

## 9. Exact-phrase and keyword search alongside semantic search
Status: implemented
**What the user gets:** Searching `"joe's pizza"` or a hashtag finds videos that contain those exact words. Today embedding search can rank a video lower even when it says the exact name.
**Why it fits:** `Collection.search` (src/collection.py) only queries by embedding. The full document text (transcript, OCR, caption) is already stored, and Chroma supports `where_document={"$contains": ...}`.
**Plan:** Parse quoted phrases out of the query in `search` (app.py). Pass them to `Collection.search` as a `where_document` `$contains` / `$and` filter, and embed the rest of the query (or the phrase itself if nothing else is left). Apply the filter in `_available` too, so the count clamp stays correct. Add a hint about quotes to the search placeholder.
**Files:** src/collection.py, app.py, templates/profile.html, test_collection.py
**Effort:** small
**Risks / open questions:** `$contains` is case-sensitive in Chroma. Either lowercase the stored documents on add (this needs a backfill) or search a few case variants.
**Done when:** A quoted query returns only videos whose document contains the phrase, ranked semantically, with filters still applied. Tests cover a quoted-only query and a mixed query.
**Implementation notes:** Quoted phrases (straight or curly quotes) are parsed by `split_phrases` in src/collection.py and passed to `Collection.search(..., phrases=)`, which builds a `where_document` filter used by both `_available` (so the count clamp stays right) and `_query`. Several phrases are combined with `$and`. Case: instead of `$contains` with case variants or lowercasing stored documents, each phrase becomes a Chroma `$regex` with the `(?i)` flag (the phrase is escaped, and the whitespace between words matches any run of whitespace, so line breaks in transcripts still match). This is fully case-insensitive and needs no data migration, but it requires Chroma 1.x (installed: 1.5.9; requirements.txt leaves chromadb unpinned). In app.py, `run_search` embeds the unquoted words, or the phrases themselves when nothing else was typed. Only text queries are affected, not `similar=`. "Show more" paging is unchanged because the filter is applied inside `Collection.search` before the offset slice. The placeholder in templates/profile.html now mentions quotes. Files: src/collection.py, app.py, templates/profile.html, test_collection.py. Added 3 tests to test_collection.py (phrase parsing, quoted-only with case/line-break/platform filter, mixed and multi-phrase). The fake embedding model now lowercases its word. Suite: 94 passed, 1 failure unrelated to this change (test_processor::test_transcribe). Deferred: unquoted hashtags are still searched only by meaning; quote them for an exact match. There is no app-level test, because importing app.py loads the real model and database.

## 10. Hide weak matches
Status: implemented
**What the user gets:** A nonsense or very specific query says "No strong matches" instead of showing the nearest (irrelevant) videos. Borderline results are visually marked.
**Why it fits:** `_query` (src/collection.py) always returns `n_results` hits and drops the distances (`include=["metadatas"]`), so every search looks equally confident.
**Plan:** Include `distances` in `_query` and return them with the results. In `run_search`, split results at a threshold (a constant, tuned on the real library): show strong matches normally and put the rest behind a "Show weaker matches" button. Pass a flag to _video_section.html to render the empty/weak state.
**Files:** src/collection.py, app.py, templates/_video_section.html, static/profile.js, test_collection.py
**Effort:** small
**Risks / open questions:** The threshold depends on the embedding model and distance metric. Log distances for a few real queries before picking it.
**Done when:** Results past the threshold are hidden by default, and a test with fake distances covers the split and has_more paging.
**Implementation notes:** `_query` (src/collection.py) now includes distances. `Collection.search(..., with_distances=True)` returns them, and the default return shape is unchanged. The threshold is `WEAK_MATCH_DISTANCE = 1.35` in src/collection.py, with a comment on how to retune it. The collection uses Chroma's default metric (hnsw space `l2`, which is squared L2), and all-MiniLM-L6-v2 embeddings are unit length, so the distance is 2 - 2*cos and 1.35 means cosine 0.325. This was chosen by logging distances for about 35 queries against a copy of the real library (1539 videos). Gibberish and topics the library lacks ("xkcd blorp", "photosynthesis in algae", "medieval tax code", "the") had no result under 1.38. On-topic queries had their relevant results between 0.65 and about 1.30 ("pizza" 1.07/1.30, "gym" 1.09-1.29, "recipe" 0.96-1.18). The split and paging live in `page_matches(matches, offset, limit, weak)` in src/collection.py, so they can be tested without app.py. `run_search` (app.py) now returns `(page, has_more, has_weak)`. Strong pages come first, and `has_weak` is only true once the strong matches run out. `/search` takes `weak=1`, in which case the offset is a rank that continues past the strong matches, and it sends an `X-Search-Has-Weak` header on appended pages. The split applies only to plain text queries. "More like this" is not split, because there is always a nearest video worth showing, and video-to-video distances are on a different scale than a short query's. Quoted-phrase searches are not split either, because every result already contains the phrase. templates/_video_section.html: "No strong matches" with an empty grid and a "Show weaker matches" button when nothing passes the threshold. The same button replaces "Show more" after the last strong page. Weaker cards get a `weak-match` class and a "Weak match" badge (templates/_video_cards.html, static/style.css). static/profile.js: the button sends `weak=1`, turns into "Show weaker matches" when the headers say so, and removes the "No strong matches" note once cards load. The viewer's auto-load never pulls in weaker matches. `sortShownResults` keeps weaker cards after strong ones. No data migration (distances are computed at query time). Files: src/collection.py, app.py, templates/_video_section.html, templates/_video_cards.html, static/profile.js, static/style.css, test_collection.py. Added 3 tests to test_collection.py: fake-distance split and has_more paging through strong and then weak pages; the no-strong and no-weak cases; and real Chroma distances from the fake embed model. Suite: 102 passed, 1 failure unrelated to this change (test_processor::test_transcribe). Deferred: the JS couldn't be run here (no node or browser), so it was only checked by reading and by rendering the template states. The threshold is a constant, not a user setting. #4 (server-side sort over top-K) could reuse `WEAK_MATCH_DISTANCE` as its cutoff.

## 14. Re-process videos with current settings
Status: proposed
**What the user gets:** After turning on OCR or visual descriptions for an account, the user can upgrade videos that were indexed without them, which makes their on-screen text searchable.
**Why it fits:** Processing steps are per-account settings (`Processor.features`, `account_settings_route`), but they only apply to newly synced videos. `fetch_missing_details` is already a background "fill in what's missing" job with a status route to copy.
**Plan:** Record the features used in metadata (`proc_ocr`, `proc_vlm`) in `Collection.add`. Add `ids_missing_features(features)`, then a background job plus status route modelled on `fetch_missing_details` that re-runs `process_video` with the account's features and upserts the result. Add a "Re-process N videos" button to the account settings.
**Files:** src/collection.py, src/processor.py, app.py, static/settings.js, templates/accounts.html, tests
**Effort:** medium–large
**Risks / open questions:** Every video has to be downloaded again, which is slow and exposed to rate limits, so the job needs pause/cancel and a rate limit like sync. Videos processed before this change have no markers, so treat them as "unknown".
**Done when:** Only videos missing the enabled features are re-processed, the job can be stopped, and tests cover selection and metadata marking.

## 16. Keep data in the app folder no matter where it's started, and make reset.py a real reset

## 17. Refuse requests from other websites
Status: proposed
**What the user gets:** A web page open in the user's normal browser can't make ReelSearch start a sync, open login windows, fetch video details, or shut down, and it can't read the saved library through DNS rebinding.
**Why it fits:** The server listens on 127.0.0.1:5000 (app.py:1415) and has no request checks at all: no `before_request` hook, no CSRF token, no Host check. Any site can send a cross-site form POST (no CORS preflight is needed) to `/sync/instagram` (app.py:1184). That starts a sync of the first Instagram account, which opens Chrome and scrolls the saved page, the same ToS and rate-limit exposure the load-speed settings try to limit. Other targets are `/accounts/add` with `platform=tiktok&username=x` (app.py:844, which opens a browser window), `/videos/details` (app.py:1131) and `/shutdown` (app.py:1300). The Flask dev server accepts any Host header, so a DNS-rebinding page can also read `/videos?...` and `/videos/info`, which contain the user's saved videos, captions and usernames. All legitimate POSTs come from the app's own pages (the `fetch` calls in static/*.js and the template forms), and browsers attach `Origin` to them.
**Plan:** In app.py, set `app.config["TRUSTED_HOSTS"] = ["127.0.0.1", "localhost"]` (supported since Flask 3.1; Werkzeug returns 400 for any other Host). Add a `@app.before_request` guard for methods other than GET/HEAD/OPTIONS: if `Origin` is present, it must equal `request.host_url` without the trailing slash; if it's absent, the `Referer` host must match; if both are absent, allow the request so curl and scripts still work. Rejections return 403 with a short message. If the user later wants LAN access, add `REELSEARCH_ALLOWED_HOSTS` to extend the list.
**Files:** app.py, test_app.py (needs the #15 conftest, or a standalone `app.test_client()` under the same patches)
**Effort:** small
**Risks / open questions:** Whether a POST with neither Origin nor Referer should be allowed (convenient for scripts) or refused (stricter). Some privacy extensions strip Referer, but same-origin POSTs still carry Origin in current Chrome and Firefox. Check that the login-session confirm/cancel `fetch` calls in static/login.js send `Origin`.
**Done when:** Tests: a POST to `/sync/instagram` with `Origin: https://evil.example` returns 403 and starts no sync (a monkeypatched `start_sync` isn't called); the same POST with `Origin: http://127.0.0.1:5000` passes; a GET with `Host: evil.example` returns 400; a POST with no Origin or Referer follows the chosen policy. Using the app manually (search, sync, settings autosave, login, remove account, stop) works unchanged.

## 19. Stop reading the whole library on every status poll
Status: implemented
**What the user gets:** The library page and search stay responsive during a sync, and the cost of polling stops growing with the size of the library.
**Why it fits:** `loaded_urls_for_account` (app.py:273) calls `collection.get_collection()` (src/collection.py:242), which is `self.collection.get()` with Chroma's default include. That loads every record's metadata and full document (transcript, OCR text, comments) only to check which ids an account owns. It runs inside `sync_status_payload` (app.py:301), which profile.js polls every 1.2s per syncing account (static/profile.js:1695) and every 10s for every account (static/profile.js:1773), and once at the start of each `sync_platform` run. `render_profile` (app.py:645) also fetches every document on each page load, only for `len(ids)` and the metadatas, and then `library_videos` runs a second full metadata scan. The non-XHR `/videos` route (app.py:1406) fetches documents only to list ids. With 1549 videos this works, but the cost grows with the library and competes with the sync workers for the same SQLite file. `accounts_where` (src/collection.py:36) and `find` (metadatas only, src/collection.py:225) already support the cheaper queries.
**Plan:** Add `Collection.owned_ids(account_id)` returning `set(self.collection.get(where=accounts_where([account_id]), include=[])["ids"])`, and use it in `loaded_urls_for_account` (intersect with the state's `urls` as today). Have `/videos` list ids with `include=[]`. Once nothing calls `get_collection()`, remove it. Optional second step, if profiling shows a need: `stop_requested` (app.py:383) reads and parses sync_state.json in every worker loop (about 1.2 ms per parse at the current 452 KB). Replace it with a per-sync `threading.Event` set by `start_sync`'s pause path, `logout_route` and `stop_syncs`.
